# japanese-quiz-game

A Japanese quiz game built with SvelteKit, deployed to Cloudflare Workers with a D1 database.

> **Project status: scaffolding.** The toolchain, Cloudflare bindings, and test setup are wired up, but the quiz itself is not built yet. What ships today is the generated starter plus demo routes. See [Known gaps](#known-gaps) before you start.

## Stack

| Concern                | Choice                                                |
| ---------------------- | ----------------------------------------------------- |
| Framework              | SvelteKit (`next`) with Svelte 5, runes forced on     |
| Hosting                | Cloudflare Workers via `@sveltejs/adapter-cloudflare` |
| Database               | Cloudflare D1 + Drizzle ORM                           |
| i18n                   | Paraglide JS — `en` (base) and `ja`                   |
| Unit / component tests | Vitest (browser + node projects)                      |
| E2E tests              | Playwright                                            |
| Package manager        | pnpm                                                  |

SvelteKit is configured **inline in [`vite.config.ts`](vite.config.ts)** — there is no `svelte.config.js`. Experimental `async` and `remoteFunctions` are enabled there.

## Prerequisites

- **Node.js 24+** (developed on v24.16.0)
- **pnpm 11+** (developed on 11.23.0) — `npm install -g pnpm`
- A **Cloudflare account** if you want to touch the database or deploy. You can run the UI locally without one.

## Getting started

```bash
git clone <repo-url> japanese-quiz-game && cd japanese-quiz-game
```

```bash
pnpm install
```

```bash
pnpm dev
```

The app is on http://localhost:5173. Add `--open` to launch a browser: `pnpm dev -- --open`.

That is enough to work on the frontend. The database steps below are only needed if you are working on persistence.

> **Run `pnpm dev` or `pnpm build` before `pnpm check`.** `src/lib/paraglide/` is generated by the Vite plugin and is gitignored, so on a fresh clone it does not exist yet. Type-checking before the first build reports a wall of "Cannot find module '#lib/paraglide/…'" errors that resolve themselves once the directory is generated.

## Cloudflare setup

Two separate credentials are involved, and they are easy to confuse:

1. **Wrangler's login** — an OAuth session used by `wrangler d1 create`, `wrangler types`, and `wrangler deploy`. Set it up once with `pnpm exec wrangler login`, verify with `pnpm exec wrangler whoami`.
2. **A D1 API token in `.env`** — used _only_ by Drizzle Kit, which talks to D1 over HTTP rather than through the Worker binding.

### Configure `.env`

Copy the template and fill it in:

```bash
cp .env.example .env
```

| Variable                 | Where it comes from                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_ACCOUNT_ID`  | `wrangler whoami`, or the sidebar of any domain's dashboard overview                                      |
| `CLOUDFLARE_DATABASE_ID` | The UUID printed by `wrangler d1 create` — must match `database_id` in [`wrangler.jsonc`](wrangler.jsonc) |
| `CLOUDFLARE_D1_TOKEN`    | Dashboard → My Profile → API Tokens → Create Custom Token, with **Account → D1 → Edit** permission        |

Every `db:*` script throws immediately if any of the three is missing. `.env` is gitignored; never commit it.

### Point at a database

[`wrangler.jsonc`](wrangler.jsonc) declares a binding named `quizdb` against a specific `database_id`. **This does not create anything** — Wrangler looks the UUID up in your account and fails if it is not there.

If you are working against your own Cloudflare account, create your own database and use its ID:

```bash
pnpm exec wrangler d1 create quizdb
```

Put the returned UUID in both `wrangler.jsonc` (`database_id`) and `.env` (`CLOUDFLARE_DATABASE_ID`). D1 UUIDs are per-account and are not portable between contributors.

### Apply the schema

The schema lives in [`src/lib/server/db/schema.ts`](src/lib/server/db/schema.ts). There is **no `drizzle/` migrations directory committed yet**, so generate one first:

```bash
pnpm db:generate
```

```bash
pnpm db:migrate
```

For throwaway local iteration, `pnpm db:push` skips migration files and pushes the schema straight to D1. Use `db:generate` + `db:migrate` for anything that lands on main.

After changing bindings in `wrangler.jsonc`, regenerate the ambient types:

```bash
pnpm gen
```

This rewrites `worker-configuration.d.ts`. `pnpm build` and `pnpm check` both run `wrangler types --check` and will fail if it is stale.

## Internationalization

Messages live in [`messages/en.json`](messages/en.json) and [`messages/ja.json`](messages/ja.json), configured by [`project.inlang/settings.json`](project.inlang/settings.json). `en` is the base locale.

Add a key to both files, then import it from the generated runtime:

```ts
import { m } from '#lib/paraglide/messages.js'

m.hello_world({ name: 'world' })
```

`src/lib/paraglide/` is regenerated by the Vite plugin on every build — treat it as build output.

The `#lib/*` import alias maps to `./src/lib/*` (see `imports` in `package.json`). **Include the `.js` extension.** The mapping is a literal substitution with no extension inference, so `#lib/paraglide/messages.js` type-checks and `#lib/paraglide/messages` does not.

## Code style

Formatting is Prettier, configured in [`prettier.config.js`](prettier.config.js): tabs, single quotes, **no semicolons**, trailing commas, 100-column width. Run `pnpm format` before pushing. Prettier only reformats — it never renames anything.

[`eslint.config.js`](eslint.config.js) adds `@typescript-eslint/naming-convention` on top of the recommended sets:

| Kind                              | Expected                                                                  |
| --------------------------------- | ------------------------------------------------------------------------- |
| variables                         | `camelCase`, `UPPER_CASE`, `PascalCase`                                   |
| functions, parameters, properties | `camelCase`                                                               |
| types, interfaces, classes        | `PascalCase`                                                              |
| exported functions                | also `UPPER_CASE`, for `+server.ts` handlers like `export function GET()` |

The rule is scoped to `src/**` only — root build config, generated code, and `tests/` are exempt. It has **no autofixer**; renaming is a manual refactor (F2 in VS Code updates every reference).

snake_case is allowed in the places where it is the correct spelling rather than a mistake:

- **Object literal keys** — API payloads, D1 column names, env-shaped config. `{ user_id: 1 }` is fine.
- **Destructured bindings** — `const { access_token } = await res.json()` needs no rename at the boundary.
- **Keys that cannot be identifiers** — `'x-api-key'`, `'Content-Type'`.

It is deliberately **not** allowed on `typeProperty`, so interfaces and type aliases stay camelCase. The one place this bites is typing a payload inline:

```ts
// eslint-disable-next-line @typescript-eslint/naming-convention -- external API shape
const { access_token } = (await res.json()) as { access_token: string }
```

## Testing

Vitest runs two projects, split by filename:

- **client** — `src/**/*.svelte.{test,spec}.ts`, in headless Chromium via Playwright
- **server** — everything else under `src/**/*.{test,spec}.ts`, in Node

Note that `expect.requireAssertions` is on, so a test that asserts nothing fails.

Playwright's `testDir` is `./tests`. It has **no `webServer` configured**, so it will not start the app for you — start `pnpm dev` in another terminal before running E2E specs that hit the local app.

CI runs Playwright only, on push and PR to `main`/`master` ([workflow](.github/workflows/playwright.yml)). Reports upload as an artifact.

## Known gaps

Contributors should know these are outstanding rather than assume something is broken.

**Current check status:** `pnpm lint` and `pnpm check` both pass clean, before _and_ after a build. `vite build` succeeds and `wrangler types --check` reports the bindings up to date (`quizdb` is present in `Env`).

### Type-checking notes

Getting to zero errors took four fixes worth knowing about, since they explain some non-obvious config:

- **`checkJs: false` in [`tsconfig.json`](tsconfig.json).** SvelteKit defaults it to `true`, and `wrangler types` writes a `GlobalProps.mainModule` entry pointing at `./.svelte-kit/cloudflare/_worker` — together those pulled the entire compiled bundle into the type program, producing ~493 phantom errors after every build. This project has no hand-written `.js`, so nothing of ours goes unchecked.
- **`#lib/*` imports need the `.js` extension.** The alias is a literal substitution with no extension inference.
- **`Handle` and `Reroute` come from `@sveltejs/kit/hooks`, not `@sveltejs/kit`.** They moved subpath in kit `3.0.0-next.25`; the `sv` scaffold still imports them from the old location.
- **`RequestEvent.request` is read-only in kit 3.** Paraglide's scaffolded middleware assigns to it, so [`hooks.server.ts`](src/hooks.server.ts) carries a narrow cast with a comment. Runtime behaviour is unchanged. Revisit when Paraglide ships a kit-3-compatible middleware.

Generated files that builds rewrite in their own style — `worker-configuration.d.ts`, `project.inlang/.meta.json`, `project.inlang/README.md` — are listed in [`.prettierignore`](.prettierignore) so a build no longer breaks `pnpm lint`. (`src/lib/paraglide/` is already exempt via `.gitignore`, which Prettier honours.)

### Other

- **The quiz game does not exist yet.** Routes under `src/routes/demo/` are template scaffolding, and `src/lib/vitest-examples/` is sample code. Both are safe to delete once real features land.
- **The D1 binding is unused.** `getDb()` is exported but never called; no route reads or writes the database.
- **The schema is a placeholder.** `schema.ts` defines a `task` table from the Drizzle starter, not quiz data.
- **`tests/example.spec.ts` tests playwright.dev**, not this app — it is the stock Playwright example and needs replacing. CI therefore passes without testing anything about this project, and runs Playwright only: no `lint`, `check`, or unit tests.
- **`src/routes/demo/playwright/page.svelte.e2e.ts` never runs.** Playwright's `testDir` is `./tests`, so the file is orphaned.
- **`src/app.d.ts` declares `env`, `ctx`, `caches`, and `cf` twice** inside `interface Platform`. Curiously `svelte-check` does not flag it, but it should still be cleaned up.
- **`.npmrc` sets `engine-strict=true` but `package.json` has no `engines` field**, so the Node/pnpm versions above are not actually enforced.
- **No migrations are committed**, so every contributor currently has to `db:generate` for themselves. Once a real schema exists, the `drizzle/` directory should be checked in.
